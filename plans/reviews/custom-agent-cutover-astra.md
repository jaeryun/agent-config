# Astra independent review — custom-agent cutover plan

## Verdict: REQUEST_CHANGES

The native-runtime approach, ownership boundaries, separation of semantic output contracts from client-specific schemas, and refusal to treat prompt loading as behavioral proof are sound. The plan nevertheless leaves source-verifiable disable exceptions and name-keyed policy migration as future investigation, although these affect its central promises: disable builtins, preserve other users' agents, and preserve personal policy during rename. Resolve the four findings below in the plan before treating implementation as authorized or mechanically specified; no final role names are selected by this review.

This is a source review, not runtime verification. I read the complete plan and shared review contract, relevant installer/configuration/role/test sources, all six supplied native exports, pinned pi-subagents documentation and relevant installed discovery code, and relevant official OMP v18.12.1 sources. I ran no build, test, installation, model request, or delegation and changed no repository/global file.

## Required findings

### R1 — P1: OMP's disable list is name-scoped, not builtin-source-scoped

**Plan location:** §1 first boundary bullet; §4 name collision rules; §5 OMP steps 2 and 6; §6 supported collision states; §7 user-definition preservation acceptance.

**Observed evidence:** OMP's [`resolveEffectiveSubagentPolicy`, `structured-subagent.ts:349–378](https://github.com/can1357/oh-my-pi/blob/v18.12.1/packages/coding-agent/src/task/structured-subagent.ts#L349-L378) first resolves the winning discovered agent, then rejects it whenever `disabledAgents.includes(agentName)`. The check does not inspect `agent.source`. The [discovery contract](https://github.com/can1357/oh-my-pi/blob/v18.12.1/docs/task-agent-discovery.md#merge-and-collision-rules) says user/project/extension definitions can shadow bundled definitions by the same name. Current `scripts/install.mjs:276–281` checks disabled-name conflicts only against roles declared in the current YAML; `:379–387` checks the target's native files only for those configured names.

**Failure scenario [INFERENCE from source]:** The user owns an independent `.omp/agents/scout.md`, while this repository renames its own scout to `explorer`. Adding all six bundled names to `task.disabledAgents` also prevents that unrelated user scout from running. Renaming only this repository's roles does not solve the conflict, and preserving the user's file does not preserve its availability. The plan currently promises preservation while deferring the exact contradictory semantics to implementation.

**Minimal plan correction:** Record the name-scoped semantics as a confirmed limitation now. Add an explicit preflight conflict case for non-repository definitions using any name to be disabled, not merely the new managed names. Default to no mutation and report the conflict; obtain the user's decision rather than renaming, disabling, or deleting their role. State that an arbitrary profile cannot simultaneously retain such a same-name role's availability and apply the full name blacklist under this native mechanism. Bound acceptance to the effective profile/project being checked; do not imply a global installer can enumerate every future project. Add a consumer-visible fixture with an independently owned old-name role and assert the selected conflict behavior.

### R2 — P1: pi `disableBuiltins: true` does not override existing per-role overrides

**Plan location:** §5 pi steps 2 and 4; §6 user-settings preservation; §7 builtin-disable acceptance.

**Observed evidence:** In installed `node_modules/pi-subagents/src/agents/agents.js:1336–1365`, `applyBuiltinOverrides()` applies, in order, a project role override, project bulk disable, a user role override, and user bulk disable. A role override returns before the same-scope bulk-disable branch. `applyBuiltinOverride()` only assigns `next.disabled` when the override actually supplies that field (`:1278–1279`); discovery subsequently filters only `agent.disabled === true` (`:2600–2602`, also `:2730–2732`). Project `disableBuiltins: false` also prevents the user bulk-disable branch. Current `scripts/install.mjs:196–208` checks overrides only for configured worker names, which will be the new names after cutover.

**Failure scenario [INFERENCE from source]:** Existing settings contain `subagents.agentOverrides.reviewer: { thinking: "high" }`. The repository installs `code-auditor` and adds only `subagents.disableBuiltins: true`. The old builtin `reviewer` still receives its override and remains enabled; no explicit `disabled: false` is necessary. An ordinary saved personal model/effort override is therefore enough to defeat the intended cutover. A clean-profile inventory smoke would miss this.

**Minimal plan correction:** Explicitly document these exceptions and inspect effective overrides for the complete builtin inventory, including old names no longer in YAML and provider/project overlays. Reject/report conflicting overrides before target mutation unless the user separately approves a narrowly owned migration; do not silently delete their settings or add name-based disables that also affect their custom same-name roles. Add acceptance cases for a user builtin override that specifies only model/thinking, a project override, and project `disableBuiltins: false`. Verify resolved discovery and direct launch, not merely the stored boolean. The plan already calls for override checks; make this exact precedence and the fail-closed policy part of that requirement.

### R3 — P1: Unsupported native paths may still execute bundled agents rather than fail

**Plan location:** §1 overall builtin-disable goal; §5 OMP steps 3–5; §7 “default name / special paths” and “no direct-call bypass” acceptance.

**Observed evidence:** In pinned OMP [`vibe/runtime.ts:62–71`](https://github.com/can1357/oh-my-pi/blob/v18.12.1/packages/coding-agent/src/vibe/runtime.ts#L62-L71), `fast` maps to `sonic` and `good` to `task`. [`#resolveWorker`, lines 353–371](https://github.com/can1357/oh-my-pi/blob/v18.12.1/packages/coding-agent/src/vibe/runtime.ts#L353-L371), directly calls `getBundledAgent(agentName)`, not normal discovery. [`#buildSpawnOptions`, lines 1270–1340](https://github.com/can1357/oh-my-pi/blob/v18.12.1/packages/coding-agent/src/vibe/runtime.ts#L1270-L1340), passes that definition to the executor, and the first turn calls `runSubprocess()` directly at [`:1390–1391`](https://github.com/can1357/oh-my-pi/blob/v18.12.1/packages/coding-agent/src/vibe/runtime.ts#L1390-L1391). Neither the retrieved Vibe runtime nor executor source contains the `disabledAgents` guard found in normal task/eval preflight. Separately, the official [user-tagged model-agent contract](https://github.com/can1357/oh-my-pi/blob/v18.12.1/docs/task-agent-discovery.md#user-tagged-model-agents) says session-local `m1`, `m2`, etc. use the bundled generic task template under different names.

**Failure scenario [INFERENCE from source]:** Normal `task(agent: "task")` is rejected by the blacklist, but Vibe may still launch the bundled task/sonic definition. Simply marking Vibe unsupported does not make this an error boundary. The blanket “builtins disabled” claim also needs to distinguish named bundled roles from synthetic tagged-model agents that reuse their prompt. The plan recognizes Vibe investigation, but currently treats unsupported/failure behavior as if documentation could establish it.

**Minimal plan correction:** State the known routing exception now and make the user decision precise: either approve a scope that excludes these native execution paths while explicitly acknowledging that they can remain executable, or require a supported native way to disable those paths and verify that it actually rejects them. Do not promise fail-closed behavior solely through main-agent instructions, and do not add a patched runtime/shim. Include tagged-model synthetic roles in the boundary decision rather than assuming the six-name blacklist covers them. If the user requires every execution of a bundled template to be impossible, record this as an unresolved native capability prerequisite, not as an implementable guarantee of the proposed blacklist. Runtime smoke must report observed execution/rejection, not relabel execution as successful disabling.

### R4 — P1: Rename must account for user-owned per-role runtime policy, not only YAML/model settings

**Plan location:** §4 synchronized rename list; §5 OMP step 6; §5 pi step 4; §6 model/effort/private-definition preservation; §7 migration acceptance.

**Observed evidence:** The OMP [model/policy precedence documentation](https://github.com/can1357/oh-my-pi/blob/v18.12.1/docs/task-agent-discovery.md#model-and-structured-output-precedence) describes exact-name settings beyond model/advisor/prewalk: `task.agentAccountPools`, `task.agentServiceTierOverrides`, `task.agentCompactionThresholdOverrides`, and `task.agentSoftRequestBudget`. Source [`structured-subagent.ts:417–428`](https://github.com/can1357/oh-my-pi/blob/v18.12.1/packages/coding-agent/src/task/structured-subagent.ts#L417-L428) resolves service tier, compaction threshold, and account pools by the requested agent name. Account pools are an authentication-selection restriction; absence permits normal account selection instead. Pinned pi documentation likewise identifies `subagents.modelScope.agents.<name>` as per-agent restrictions (`node_modules/pi-subagents/docs/configuration.md:5`) and per-role/provider-scoped model/thinking overrides (`docs/models.md:8–14`). These user-owned keys are not all part of the current installer's managed-leaf set (`scripts/install.mjs:254–293`).

**Failure scenario [INFERENCE from source]:** A user has restricted the existing `task` role with `task.agentAccountPools.task`. The YAML and role file are renamed to `implementer`, while the unrelated-looking user setting is “preserved” under `task`. The new role no longer receives the restriction. The same class of rename changes per-role model ceilings/allowlists, billing-tier selection, and request budgets without modifying the user's chosen YAML model/effort. Byte preservation alone does not preserve policy semantics.

**Minimal plan correction:** Add an explicit audit of supported native name-keyed policy when planning a rename. For repository-owned keys, move ownership and rollback records with the approved mapping. For user-owned old-name keys, preserve them and stop/report the ambiguity until the user decides whether they follow the repository role or remain attached to another agent of that name; never automatically duplicate or move credential/account policy. No new policy framework is necessary. Add acceptance coverage showing that an old-name account restriction or model-scope restriction cannot silently disappear from the renamed role's effective policy. The plan need not inspect credentials to detect these key-level conflicts.

## Optional suggestions — not additional blockers

1. **Make personal-YAML migration operationally explicit.** The current installer reads the source YAML but its transaction/backup records cover a single target and installation manifest (`scripts/install.mjs:93–147`, `:507–541`), not source YAML or both clients as one transaction. Specify who performs the approved YAML key/reference changes, what private backup is retained, and how a partial OMP/pi cutover is reported/recovered. Distinguish repository-owned `definition` references that must follow renamed files from private definition paths that must remain untouched. Do not claim new cross-client atomicity or power-loss recovery.
2. **Keep result schemas deliberately client-specific.** The current semantic-contract direction is correct. OMP frontmatter `output` is schema data, while pi frontmatter `output` denotes an output file (`node_modules/pi-subagents/docs/agents.md:435`). If schema work becomes necessary, specify the OMP structured activation mode and the actual pi result consumer first; do not introduce a shared `output` field by name alone. The native reviewer/scout/security exports contain different schemas, so a single universal review envelope is not justified by the evidence inspected.
3. **Separate publishing from implementation approval.** §7 step 6 currently includes commit/push under the future implementation procedure. Clarify that commit/push occurs only if the implementation authorization includes publication; the present request authorizes only planning/review. This is wording/authority hygiene, not an instruction to publish now.
4. **Promote the main-only policy to the decision checklist.** §6 offers a sensible proposal but §7 step 1 omits it from the decisions to finalize. If disabling plugin builtins persists in main-only mode, account for the fact that current `requirePiSubagents()` is gated on having workers (`scripts/install.mjs:333–334`); without a loaded plugin, do not claim a live pi builtin-disable verification.
5. **Keep the current smoke's limits explicit.** `tests/pi-plugin.test.mjs:54–58,104–125` drives two known roles through an isolated local endpoint, uses `agentScope: "user"`, and checks real read results/model/effort/tool rosters. It does not cover project precedence, bulk-disable exceptions, negative launches, or a renamed-role migration. Extending those behavior boundaries is useful; replacing it with generated-frontmatter snapshots would not be.

## Unverified assumptions and scope limits

- No runtime scenarios were executed, as required by this review assignment. Failure scenarios above are marked source-derived inferences, not reproduced failures. Existing tests were read, not run; their source is not evidence that they currently pass.
- Official OMP evidence is pinned to v18.12.1. The supplied six binary exports were inspected as provided; I did not independently rerun the export or verify that a local executable exactly matches the remote tagged source. The docs themselves still list five roles in some inventory prose, so the six exported files remain the supplied inventory evidence rather than an excuse to omit `seance`.
- pi discovery evidence is from the installed package identified by the brief as 0.79.1. Behavior of other accepted 0.79.x patches is unverified. No alternate plugin implementation was considered.
- I did not inspect private YAML, global client settings, credentials, user histories, arbitrary project overrides, or authentication state. The report establishes possible supported-input conflicts, not that these conflicts exist in the user's actual profile.
- Source inspection establishes Vibe's direct bundled route and the lack of a disable-list guard in the inspected runtime/executor. Availability of Vibe tools in a particular live session, possible supported top-level feature disable controls, and tagged-model runtime behavior remain to be verified before choosing an enforceable policy.
- Final names, capability widening, main-only behavior, and removal/exclusion of special native workflows remain user decisions. No decision in this report authorizes any of them.
- Role prompts are not a security sandbox. The plan's distinction is appropriate; neither this review nor a deterministic transport smoke proves model compliance, visual-model capability, or complete isolation from ambient extensions.

## Integration direction

Retain the native OMP extension-package and pi-subagents design. Tighten the plan around exact effective disable semantics, explicit conflict/no-mutation outcomes, and semantic preservation of name-keyed user policy; the parent can integrate those corrections without implementing a new runner or choosing the user's role names.
